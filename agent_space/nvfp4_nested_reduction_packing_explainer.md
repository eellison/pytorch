# NVFP4 Nested-Reduction Packing Explainer

This commit teaches nested-reduction codegen the NVFP4 packing shape that appears after an RMSNorm-style producer. The grouped reduction still computes one scale per reduction group, but the final packed output is at pair resolution: two normalized float values are converted by inline asm into one e2m1x2 byte. Before this change, nested reduction codegen could handle the grouped amax/scale part, but it did not have a way to run a follow-on pointwise epilogue over half of the parent reduction axis while reusing the values already loaded for the grouped stage.

The scheduler now recognizes those pair-resolution consumers as a separate parent-half pointwise domain instead of mixing them into the grouped reduction schedule. SIMD codegen builds a derived iteration family for that half-resolution view, maps pair coordinates back to the original parent tile, and emits the pointwise packing after the grouped amax/scale work inside the same Triton kernel.

The key implementation detail is the value remapping. The grouped stage records the parent-tile loads and reduced values it produced; the parent-half epilogue looks those values up from the CSE store cache or recorded stage loads. Full parent-tile values are reshaped to `[group, pair, lane]`, split with `tl.split`, and resolved lane-by-lane when the inline asm asks for the even or odd value. Grouped scale values are broadcast back to pair resolution so the same per-group scale is used for both values in each packed byte.

The tests compare the fused nested-reduction kernel against an unnested Inductor compile, requiring exact packed bytes and close scale values. They also check the generated kernel shape: a single kernel, expected load counts, a minimum reduction block size, and the presence of `tl.split`, `tl.broadcast_to`, and the NVFP4 inline asm instruction. A combo-kernel regression test separately makes sure combo-kernel grouping does not accidentally absorb nested reductions.
