## Graph Replay Harness

For runtime rows below, use CUDA event timing around replay of a captured compiled callable. Use `mode="reduce-overhead"` for cudagraph-oriented PRs and `mode="max-autotune"` only when the PR concerns autotune selection.

```python
import torch

def replay_ms(fn, args, *, mode="reduce-overhead", warmup=10, iters=100):
    compiled = torch.compile(fn, mode=mode)
    for _ in range(warmup):
        compiled(*args)
    torch.cuda.synchronize()

    graph = torch.cuda.CUDAGraph()
    with torch.cuda.graph(graph):
        compiled(*args)

    start = torch.cuda.Event(enable_timing=True)
    end = torch.cuda.Event(enable_timing=True)
    start.record()
    for _ in range(iters):
        graph.replay()
    end.record()
    torch.cuda.synchronize()
    return start.elapsed_time(end) / iters
```

## Confidence And Caveats

Confidence is high that the ranked runtime rows are reachable H1 2026 eellison-authored Inductor/PT2 PRs in the local `HEAD` slice. Confidence is medium on the exact rank ordering because I did not run benchmarks; ranking is based on blast radius, PR descriptions, and directly visible tests/knobs.

The graph-replay shapes are concrete starting points, not claimed winning shapes. For cudagraph-control PRs, internal Inductor cudagraph counters and skips should be measured alongside external `torch.cuda.CUDAGraph` replay timing, because an outer capture can hide some Python overhead that the PR itself is meant to control.

Nested-reduction-only PRs were intentionally excluded even when they also mention NVFP4 or packing. The low-precision non-nested impact is covered by #177922 and #172497.
