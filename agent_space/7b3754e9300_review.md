## Summary

Request changes. The implemented index-inversion paths are numerically sound, but the optimization remains composition-dependent and the scale-swizzle correctness test can miss localized layout errors.

## 1. Composition-dependent fusion

The layout-consumer reindexing path still requires a plain `SchedulerNode`. Common trailing pointwise operations can either change the condition that triggers flattening or cause the consumer to become a `FusedSchedulerNode`, preventing inversion.

Observed kernel counts:

```text
swizzle(realize(x + 1))                 1 kernel
swizzle(realize(x + 1)) + 1             2 kernels
realize(swizzle(realize(x + 1))) * 3    2 kernels
```

Relevant code:

- `torch/_inductor/scheduler.py:7032`: flattening eligibility checks
- `torch/_inductor/scheduler.py:7078`: rejection of non-`SchedulerNode` consumers

Recommended fix: make flattening eligibility depend on the consumer's logical loop rank and equal-numel relationship, not only write-layout mismatch. Then either ensure the producer-to-layout edge is transformed before downstream fusion or safely support the relevant leaf inside a fused consumer.

Add a regression test with a trailing pointwise operation and require one generated kernel.

## 2. Weak scale-swizzle correctness check

`test_rmsnorm_block_scale_swizzle` uses `atol=rtol=1e-2`, while scale values average around `0.007`. A localized incorrect row permutation with maximum error `0.00981` passes that tolerance. The kernel-form test counts stores but does not verify the swizzled store index.

Relevant tests:

- `test/inductor/test_nested_reduction.py:299`
- `test/inductor/test_nested_reduction.py:1404`

Recommended fix: validate the scale output separately with a tight tolerance or structured inputs producing clearly distinct scale values. Also consider checking the generated store-index expression.
